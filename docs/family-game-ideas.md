# 三个家庭游戏 idea

配套阅读:[nakama-godot-guide.md](./nakama-godot-guide.md)

三个 idea 刻意选在**不同的轴**上,而不是三个换皮的同类游戏:

| | 玩法轴 | 同步方式 | 架构路线 | 难度 | 到 MVP |
|---|---|---|---|---|---|
| ① 我们家的冷知识 | 竞争 | 回合制 | A(中继) | ⭐⭐ | 2–3 周 |
| ② 拆弹小队·家庭版 | 强制合作 | 实时 | A(中继) | ⭐⭐⭐ | 3–4 周 |
| ③ 家庭小镇 | 共建 | 异步 | B(权威) | ⭐⭐⭐⭐ | 6–8 周 |

建议顺序就是 ①→②→③,难度和 Nakama 能力覆盖都是递进的。

---

## ① 《我们家的冷知识》— 家庭私有题库答题擂台

### 核心 hook

题库不是百科题,是**只有你家人才答得上来的题**:

> - 爸爸最不能忍的一道菜是?
> - 2019 年去青岛那次,是谁把行李箱落在酒店了?
> - 妈妈的手机密码改过几次?
> - 家里那只猫第一次被抓到上桌是哪一年?

出题权也在家里人手上——任何人都能在游戏里加题。这条让游戏**永远玩不腻**,因为内容是全家一起长出来的,而且加题这件事本身就很好玩。

### 为什么适合家庭

- **零学习成本**。四个按钮选答案,爷爷奶奶都会。
- **年龄差不吃亏**。小孩对"最近的事"记得比大人清楚,大人对"十年前"更强,天然平衡。
- **手机就能玩**。Web 导出 + 家里 WiFi,发个链接全家进。
- **一局 5 分钟**。饭后甜点时间刚好一局。

### 用到的 Nakama 能力

| 能力 | 用在哪 |
|---|---|
| 设备认证 | 一键进,不用注册 |
| **Storage** | 题库(全家共享,`permission_read=2`)、每人的答题历史 |
| **Leaderboard** | 本月冠军、总榜、"最会出题的人"(题目被答错率最高) |
| MultiplayerBridge · 具名房 | `join_named_match("huang-family")`,全家永远进同一间 |
| Group | 一个家庭 = 一个 group,可以有多个家庭各玩各的 |
| Notification | "小明加了 5 道新题,来挑战" |

### 架构

**路线 A。** 回合制、全员互相信任,权威服务器纯属过度设计。

题目分发有个小坑要注意:题库存在 Nakama storage 里,但**如果每个客户端各自去读题库再自己抽题,大家抽到的题不一样**。解法是让房主(peer 1)抽题后用 `@rpc("authority", "call_local")` 广播题号,其他人按题号去本地题库取题。

```gdscript
# 房主抽题并广播
@rpc("authority", "call_local", "reliable")
func start_question(question_index: int, deadline_msec: int) -> void:
	current = question_bank[question_index]
	_show(current, deadline_msec)

# 所有人提交答案
@rpc("any_peer", "call_local", "reliable")
func submit_answer(choice: int, elapsed_msec: int) -> void:
	var peer := multiplayer.get_remote_sender_id()
	answers[peer] = {"choice": choice, "ms": elapsed_msec}
```

计分:答对得基础分,**再按速度加成**。这个设计能制造"最后一题翻盘"的戏剧性,比单纯比答对数好玩得多。

### MVP 范围(第一个能玩的版本)

砍到不能再砍:

- [ ] 设备认证 + 具名房进同一间
- [ ] 题库硬编码 20 道题在 `res://questions.json` 里(**先不做云端题库**)
- [ ] 4 选 1,15 秒倒计时
- [ ] 10 题一局,结算显示排名
- [ ] Web 导出,手机能打开

**这个 MVP 里 Nakama 只干两件事:认证 + 中继。** 跑通了再加 storage 题库、leaderboard、加题界面。

### 扩展方向

- **老照片题**:上传家庭照片当题面("这是哪年拍的?")。照片存 Nakama storage 或直接放静态站点。
- **押注模式**:答题前押分,答对翻倍答错扣掉。小孩很吃这套。
- **年度颁奖**:年底自动统计"最强大脑""最会瞎猜""出题最刁钻"。

## ② 《拆弹小队·家庭版》— 不对称强制合作

### 核心 hook

灵感来自 *Keep Talking and Nobody Explodes*,但把它变成**家庭协作**:

- **操作方**(电脑/平板):看得见装置,看不见说明书。
- **指挥方**(手机,可以多人):看得见说明书,看不见装置。

两边**必须靠说话**才能通关。游戏本身不提供任何跨端的信息通道——这是设计的核心,不是限制。

> 操作方:"我这有个四色按钮,红黄蓝绿,上面写着 3"
> 指挥方:"等等……如果数字是 3 而且有蓝色,先按最后一个;有绿色吗?"
> 操作方:"有!"
> 指挥方:"那不对,那是另一条规则——你先告诉我序列号是奇数还是偶数"

### 为什么适合家庭

- **彻底抹平年龄和游戏水平差异**。指挥方不需要任何手速和操作,识字就行。小孩当指挥、爸妈当手,或者反过来,都成立。
- **强制面对面说话**。这可能是它最大的价值——不是各自盯着屏幕,而是全家围在一起喊。
- **人数弹性**。1 个操作方 + 1~4 个指挥方,来几个人都能玩。
- **难度可调**。模块数量和时限直接控制难度,给小孩玩就 2 个模块 5 分钟。

### 用到的 Nakama 能力

| 能力 | 用在哪 |
|---|---|
| 设备认证 | 同上 |
| MultiplayerBridge | 中继输入和装置状态 |
| **Match presence** | 谁在线、谁是操作方、谁是指挥方 |
| Storage | 通关记录、解锁的模块 |
| Leaderboard | 最快通关时间(全家协作成绩,不是个人榜) |

### 架构

**路线 A**,但和 idea ① 有个本质区别:**两端跑完全不同的场景**。

```gdscript
func _on_match_joined() -> void:
	# 第一个进来的人当操作方,其余是指挥方
	if multiplayer.is_server():
		get_tree().change_scene_to_file("res://src/world/BombDefuser.tscn")
	else:
		get_tree().change_scene_to_file("res://src/world/ManualReader.tscn")
```

同步量极小——只有"哪个按钮被按了""线被剪了""还剩几秒"。带宽压力几乎为零,`reliable` 全程管够,不用管插值。

**唯一需要认真设计的是随机种子的同步**。装置的配置(几个模块、什么颜色、序列号是多少)必须两端一致:

```gdscript
# 房主生成种子并广播,双方用同一个种子生成同一个装置
@rpc("authority", "call_local", "reliable")
func setup_bomb(seed_value: int) -> void:
	var rng := RandomNumberGenerator.new()
	rng.seed = seed_value
	_generate_modules(rng)   # 两端跑同样的代码,得到同样的装置
```

这是个非常好的练习——**它教你的是确定性(determinism),这个概念在所有联机游戏里都要用。**

### MVP 范围

- [ ] 具名房 + 自动分配角色(第一个进来的当操作方)
- [ ] **只做一个模块类型**:剪线。6 根不同颜色的线,按规则剪其中一根
- [ ] 说明书页面是纯静态 UI,把规则写死
- [ ] 5 分钟倒计时,剪错直接爆炸
- [ ] 操作方剪线 → RPC 广播 → 两端同时看到结果

一个模块就够验证整套机制了。跑通之后加模块是**纯内容工作,没有新技术**——这正是好的 MVP 边界。

### 扩展方向

- **模块库**:按钮序列、摩斯电码、记忆矩阵、迷宫。每加一个模块,复玩性翻一倍。
- **家庭定制模块**:序列号换成家里的门牌号,密码是某人生日。
- **反过来玩**:操作方蒙眼,指挥方口述操作。

## ③ 《家庭小镇》— 异步持久世界

### 核心 hook

全家共建一个小镇,**离线的时候世界照样在走**。

- 妈妈上午种下的番茄,晚上小孩上线时熟了,可以帮她收(收成给她,小孩拿"帮工费")
- 爸爸攒的木材放在公共仓库,谁都能拿去盖房子
- 每周有一个全家共同目标:凑齐材料盖一座桥 / 办一场镇上的祭典
- 每个人上线时看到的第一件事是:**我不在的这段时间,家里人干了什么**

它不比拼手速,也不比谁答得快——**它靠"惦记"驱动**。你会在通勤路上想起来"该去看看番茄熟没熟"。

### 为什么适合家庭

- **不需要凑时间**。这是它相对前两个 idea 最大的优势——一家人时间对不齐是常态。
- **合作而非竞争**。没有输家,不会有小孩玩输了闹脾气的场面。
- **留痕**。玩上一年,这个小镇本身就是一份家庭记录:谁盖的哪栋房子、哪次祭典是为了谁的生日办的。
- **低强度**。每天上线三分钟也能玩下去。

### 用到的 Nakama 能力

**这个 idea 会把 Nakama 用满,它就是为了这个而设计的。**

| 能力 | 用在哪 |
|---|---|
| **权威 match handler** | 世界状态的唯一真相,tick 里推进作物生长、天气、事件 |
| **Storage(`permission_write=0`)** | 玩家背包、建筑、镇子布局。**客户端不可写** = 改不了存档 |
| **RPC** | 所有会改变世界的操作(种植/收获/建造)都走 RPC,服务端校验 |
| **Notification** | "你的番茄熟了""爸爸盖好了磨坊""本周目标还差 20 块石头" |
| **Group** | 一个家庭 = 一个 group,组内共享仓库 |
| Leaderboard | 本周贡献榜(温和的、非零和的竞争) |
| Chat(persistent) | 镇上的留言板,离线也能看到别人留的话 |

### 架构

**路线 B,而且没得选。** 异步 + 离线推进这两个需求,中继模式根本做不了——没人在线时谁来推进世界?

关键设计:**离线时间不靠 tick 累加,靠时间戳算**。

```lua
-- ❌ 错:世界得 24 小时挂着 tick,而且服务器重启就丢进度
state.crops[id].growth = state.crops[id].growth + 1

-- ✅ 对:只存"种下的时刻",要用的时候现算
-- 种植时
local crop = { kind = "tomato", planted_at = os.time(), plot = plot_id }

-- 任何人来看这块地时才计算
local function crop_stage(crop)
    local elapsed = os.time() - crop.planted_at
    return math.min(math.floor(elapsed / 3600), MAX_STAGE)   -- 每小时长一级
end
```

这样服务器重启、断电、迁移都不影响进度,而且省掉了绝大部分 tick 开销。`match_loop` 只需要处理**在线玩家的操作**和**低频的全局事件**(比如每小时判定一次天气)。

`match_terminate` 和 `match_leave` 里一定要 `nk.storage_write` 落盘——demo 的 `world_control.lua` 就是这么做的,直接抄。

### MVP 范围

范围控制在这个 idea 上尤其重要,它太容易做成一个无底洞。狠狠砍:

- [ ] 权威 match handler 跑起来,能广播状态
- [ ] **一块地、一种作物、一个生长阶段**(种下 → 1 小时后可收)
- [ ] 种植和收获各一个 RPC,服务端校验(这块地是不是空的?作物熟了没?)
- [ ] 进度存 storage,`permission_write=0`
- [ ] 一个共享仓库,能存能取
- [ ] 上线时显示"你不在的时候发生了什么"的流水

**先不做**:建筑、天气、祭典、地图编辑、美术。等这个循环能跑通一周不出 bug,再往上加。

### 扩展方向

- **纪念日事件**:某人生日那天镇上自动放烟花,全家都收到通知。
- **家务映射**:现实里完成一件家务 → 镇子里获得资源。把 idea ①②③ 之外那个"家务游戏化"的点子并进来。
- **年鉴**:每年底自动生成一张镇子全景图 + 这一年的大事记。

---

## 怎么选

**如果你想尽快让全家玩上你做的东西 → ①。** 两三周就能有个能发链接的成品,而且题库是家人一起填的,他们会有参与感。这个正反馈对坚持学下去很重要。

**如果你更想学"联机游戏到底怎么回事" → ②。** 确定性、状态同步、角色分化,这些概念在里面都是必修课,但规模又小到可控。

**如果你想要一个能玩几年的东西 → ③。** 但**别把它当第一个项目**——它需要的服务端功力,得先在 ①② 上练出来。

三个都做的话,顺序就是 ①→②→③。
