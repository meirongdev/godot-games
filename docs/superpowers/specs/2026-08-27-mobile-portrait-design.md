# 手机竖屏可玩 — 设计文档

状态:设计已确认,待实施

## 1. 目标

**家里人拿起手机、竖着拿,打开网页就能玩。** 不需要横屏,不需要装任何东西。

现在的 UI 是为 1280×800 桌面做的,手机上打不开(见 §3 实测)。

**非目标:** 原生 App、PWA 安装、手势操作、横屏专用布局。

## 2. 已定决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **竖屏优先** | 家里人拿起手机默认是竖的。要求先横屏等于多一道门槛 |
| 2 | **一套布局走天下**,桌面也用单列(限宽居中) | 只维护一套、只测一套。两套布局必然漂移,而这个项目已经被「本地能跑线上不行」咬过两次 |
| 3 | 基准分辨率改成**竖屏方向**,短边决定缩放 | 见 §4,这是「手机上一切都是 30%」的根因 |
| 4 | 触控尺寸和字号**收进 `family.tres` 主题** | 现在散在四个场景的 `custom_minimum_size` 里,改一处漏三处 |
| 5 | 大厅用**分段切换**(房间/在线/聊天)而不是滚动长页 | 竖屏一屏放不下三块内容;切换比滚动更适合单手 |

### 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 提示「请横屏使用」,布局不动 | 改动最小,但把门槛推给用户。且横屏下短边只有 390,同样要重做缩放 —— 省不掉多少 |
| 手机版和桌面版两套 `.tscn`,运行时选 | 两套必然漂移,回归测试翻倍。这个项目的教训是「分叉就是故障的土壤」 |
| 只改缩放,保留左右两栏 | 390 逻辑宽塞两栏,每栏不到 200 —— 房间名和房主名都放不下 |

## 3. 数据依据(2026-08-27 实测)

无头 Chrome + CDP 设备模拟,390×844 CSS 像素 / DPR 3:

| 项 | 实测 | 应有 |
|---|---|---|
| 内容缩放 | **0.30** | ≈ 1.0 |
| 按钮实际高度 | **约 18pt** | ≥ 44pt(iOS HIG) |
| 登录页内容占屏宽 | **35%** | ≈ 100% |
| 登录页空白占比 | **约 65%** | — |
| 大厅逻辑视口 | **1280×2767** | ≈ 400×866 |

大厅在竖屏下:左右两栏被拉成 2767 逻辑像素高,在线/聊天面板高得离谱,聊天输入框被挤到屏幕最底角。

**缩放系数的经验规律(实测确认):** `canvas_items` + `expand` 的缩放是
`min(窗口宽/基准宽, 窗口高/基准高)`。基准 1280×800、屏幕 390×844 时
`min(0.30, 1.06) = 0.30` —— 与实测的 30% 吻合。

## 4. 缩放策略

**短边决定一切。** 手机竖屏短边 390,要装下 1280 逻辑像素只能缩到 30%。所以基准分辨率必须是竖屏方向的。

起步值 **400×640**:

| 屏幕 | 缩放 | 内容列(400 逻辑宽)实际宽度 |
|---|---|---|
| 手机竖屏 390×844 | 0.98 | 392px,铺满 |
| 手机竖屏 430×932 | 1.08 | 430px,铺满 |
| 手机横屏 844×390 | 0.61 | 244px,偏小但可用 |
| 桌面 1280×800 | 1.25 | 500px 居中 |
| 桌面 1920×1080 | 1.69 | 676px 居中 |

⚠️ **这两个数字是起步值,实施时要对着真机尺寸截图微调。** 规则(短边决定、竖屏方向基准)是设计决策;`400×640` 是可调参数。手机横屏是已知的弱项,取舍见 §2 决策 1。

## 5. 布局:一套单列

四个场景统一成:

```
MarginContainer (边距 16)
└── CenterContainer
    └── VBoxContainer (custom_minimum_size.x = 400)
```

限宽的机制:`CenterContainer` 把子节点压到它的**最小尺寸**并居中,所以
`VBoxContainer` 就是恰好 400 逻辑宽 —— 不需要额外的 max-width 逻辑。

配合 §4 的基准分辨率,两端正好对上:

- 手机竖屏 390×844 → 逻辑视口宽 **正好 400**,单列铺满,左右无留白;
- 桌面 1280×800 → 逻辑视口 1024×640,400 宽的单列居中,两侧各留 312。

### 5.1 登录

已经是单列,只改:限宽、控件高度交给主题、标题字号随基准缩小。

### 5.2 大厅

```
┌──────────────────┐
│  家庭游戏大厅     │  ← 标题
├──────────────────┤
│ [房间] 在线  聊天 │  ← 分段切换(三个 Button 互斥)
├──────────────────┤
│ 石头剪刀布        │
│ 小明的房间  2/8   │  ← 当前分段的内容,填充剩余高度
│ ────────────────  │
│ 小红的房间  1/8   │
│                  │
├──────────────────┤
│ 石头剪刀布 ▾      │  ← 底部固定操作条
│ 房间名(可留空)   │
│ ┌──────────────┐ │
│ │    建  房     │ │
│ └──────────────┘ │
└──────────────────┘
```

- 原来的 `HBox/Left`(在线+聊天)和 `HBox/Right`(房间+建房)合并成一列。
- 分段切换用 **`TabContainer`**,三个子节点 `Rooms` / `Online` / `Chat`
  (节点名用 ASCII,因为 `.gd` 里的路径是硬编码字符串)。
  `TabContainer` 自己管可见性,不用手写互斥逻辑。
- 「建房」操作条**始终可见**,不随分段切换 —— 它是主操作。
- 「刷新」按钮删掉:列表本来每 3 秒自动轮询,手机上这个按钮只是占地方。

### 5.3 房间

```
┌──────────────────┐
│ 小明的房间 · 猜拳 │ [离开] │
├──────────────────┤
│ 👑小明(我)✓ 小红… │  ← 玩家名单改成横向紧凑一行
├──────────────────┤
│                  │
│    (游戏区)      │  ← 填充,竖直空间全给它
│                  │
├──────────────────┤
│ 准备 ⬤    [开始] │  ← 底部固定
└──────────────────┘
```

玩家名单从竖着的 `ItemList` 改成横向紧凑列表,把竖直空间让给游戏区。

## 6. 触控尺寸收进主题

`family.tres` 现在只有 `default_font` + `default_font_size = 20`。加上:

| 控件 | 属性 | 值 |
|---|---|---|
| `Button` | 最小高度 | 48 |
| `LineEdit` | 最小高度 | 48 |
| `OptionButton` | 最小高度 | 48 |
| `CheckButton` | 最小高度 | 48 |

各场景里散落的 `custom_minimum_size` 相应删掉(手势按钮那种刻意要方形的除外)。

**为什么值得单独做这一步:** 现在「按钮多高」这件事有四个来源,加第五个游戏时必然又漏一个。收到主题里之后,`加新游戏` 只要用 `Button` 就自动是可点的尺寸。

## 8. 已知限制

- **软键盘遮挡。** 聊天输入框获得焦点时,手机软键盘可能挡住内容。Godot Web 的虚拟键盘支持是 experimental(`html/experimental_virtual_keyboard=true`),先用自带的,真机不行再单独处理。
- **手机横屏偏小**(缩放 0.61)。竖屏优先的代价,见 §2 决策 1。
- **`ItemList` 的触摸滚动手感**未在真机验证过,无头浏览器测不出手感。
- **标签页隐藏时引擎停转。** 这不是本次引入的,但手机上切后台/锁屏必然触发,靠 `ensure_socket_async()` 的断线自愈兜住(已实施,commit `6db2af1`)。
