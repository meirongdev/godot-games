# 手机竖屏可玩 — 设计文档

日期:2026-08-27
状态:**已实施**(2026-08-27,分支 `feat/mobile-portrait`)
相关:[game-lobby-design.md](2026-08-25-game-lobby-design.md) · [deployment-contract.md](../../deployment-contract.md)

---

## 1. 目标

**家里人拿起手机、竖着拿,打开网页就能玩。** 不需要横屏,不需要装任何东西。

现在的 UI 是为 1280×800 桌面做的,手机上打不开(见 §3 实测)。

**非目标:** 原生 App、PWA 安装、手势操作、横屏专用布局。

## 2. 已定决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **竖屏优先** | 家里人拿起手机默认是竖的。要求先横屏等于多一道门槛 |
| 2 | **一套布局走天下**,桌面也用单列(限宽居中) | 只维护一套、只测一套。两套布局必然漂移,而这个项目已经被「本地能跑线上不行」咬过两次 |
| 3 | 基准分辨率改成**竖屏方向**,短边决定缩放 | 见 §4,这是「手机上一切都是 30%」的根因 |
| 4 | 触控尺寸和字号**收进 `family.tres` 主题** | 现在散在四个场景的 `custom_minimum_size` 里,改一处漏三处 |
| 5 | 大厅用**分段切换**(房间/在线/聊天)而不是滚动长页 | 竖屏一屏放不下三块内容;切换比滚动更适合单手 |

### 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 提示「请横屏使用」,布局不动 | 改动最小,但把门槛推给用户。且横屏下短边只有 390,同样要重做缩放 —— 省不掉多少 |
| 手机版和桌面版两套 `.tscn`,运行时选 | 两套必然漂移,回归测试翻倍。这个项目的教训是「分叉就是故障的土壤」 |
| 只改缩放,保留左右两栏 | 390 逻辑宽塞两栏,每栏不到 200 —— 房间名和房主名都放不下 |

## 3. 数据依据(2026-08-27 实测)

无头 Chrome + CDP 设备模拟,390×844 CSS 像素 / DPR 3:

| 项 | 实测 | 应有 |
|---|---|---|
| 内容缩放 | **0.30** | ≈ 1.0 |
| 按钮实际高度 | **约 18pt** | ≥ 44pt(iOS HIG) |
| 登录页内容占屏宽 | **35%** | ≈ 100% |
| 登录页空白占比 | **约 65%** | — |
| 大厅逻辑视口 | **1280×2767** | ≈ 400×866 |

大厅在竖屏下:左右两栏被拉成 2767 逻辑像素高,在线/聊天面板高得离谱,聊天输入框被挤到屏幕最底角。

**缩放系数的经验规律(实测确认):** `canvas_items` + `expand` 的缩放是
`min(窗口宽/基准宽, 窗口高/基准高)`。基准 1280×800、屏幕 390×844 时
`min(0.30, 1.06) = 0.30` —— 与实测的 30% 吻合。

## 4. 缩放策略

**短边决定一切 —— 但只对手机和横屏成立。** 手机竖屏短边 390,要装下 1280 逻辑像素只能缩到 30%。所以基准分辨率必须是竖屏方向的。

落地值 **432×700**(设计期写的 400×640 是起步值,实施时按下面两条理由调整):

- **宽 432** = 16 边距 ×2 + **400 内容列**。手机竖屏宽高比(0.45~0.56)全部低于分界线 `432/700 = 0.617`,所以一律**宽度受限** —— 逻辑视口恒为 432 宽、内容列恒为 400。这不是近似:在宽度受限区间里 `逻辑视口宽 ≡ 基准宽` 是恒等式,所以「内容列正好 400」对**任何**手机都成立,不需要 max-width 逻辑。
- **高 700 而不是 640**:基准高度**对手机毫无影响**(手机全程由宽度决定),只管平板和桌面。640 会让 iPad 768×1024 缩放到 1.60 —— 640px 宽的列占屏宽 83%、按钮 70pt+,像把手机界面拿放大镜看。700 压到 1.46。**不要再往上调**:750 会把分界线压到 0.576,贴上最方的真机 360×640(0.5625),有把边缘机型翻进未测过的高度受限区的风险。

| 屏幕 | 缩放 | 逻辑视口 | 内容列(400 逻辑宽)实际宽度 |
|---|---|---|---|
| 手机竖屏 390×844(实测) | 0.90 | **432×934** | 361px,占屏宽 92.6% |
| 手机竖屏 360×800 | 0.83 | 432×960 | 333px,占屏宽 92.6% |
| 手机竖屏 430×932 | 1.00 | 432×936 | 398px,占屏宽 92.6% |
| 手机横屏 844×390 | 0.56 | 1516×700 | 223px(26%),已知弱项 |
| 平板 768×1024 | 1.46 | 526×700 | 585px,偏大 |
| 桌面 1280×773(实测) | 1.10 | **1159×700** | 442px 居中 |
| 桌面 1920×1080 | 1.54 | 1245×700 | 617px 居中 |

⚠️ **「短边决定」这个直觉只在宽高比 < 0.617 或 > 1 时成立。** 落在 `0.617~1`(接近方形的竖屏,也就是平板)时是**高度**受限:iPad 768×1024 的短边是 768,但决定缩放的是高度。高度受限没有上界 —— 横屏、桌面、超宽屏全在内。

## 5. 布局:一套单列

四个场景统一成:

```
MarginContainer (边距 16)
└── CenterContainer
    └── VBoxContainer (custom_minimum_size.x = 400)
```

限宽的机制:`CenterContainer` 把子节点压到它的**最小尺寸**并居中,所以
`VBoxContainer` 就是恰好 400 逻辑宽 —— 不需要额外的 max-width 逻辑。

配合 §4 的基准分辨率,两端正好对上:

- 手机竖屏 390×844 → 逻辑视口宽 **正好 400**,单列铺满,左右无留白;
- 桌面 1280×800 → 逻辑视口 1024×640,400 宽的单列居中,两侧各留 312。

### 5.1 登录

已经是单列,只改:限宽、控件高度交给主题、标题字号随基准缩小。

### 5.2 大厅

```
┌──────────────────┐
│  家庭游戏大厅     │  ← 标题
├──────────────────┤
│ [房间] 在线  聊天 │  ← 三个 toggle Button
├──────────────────┤
│ 石头剪刀布        │
│ 小明的房间  2/8   │  ← 当前分段的内容,填充剩余高度
│ ────────────────  │
│ 小红的房间  1/8   │
│                  │
├──────────────────┤
│ 石头剪刀布 ▾      │  ← 底部固定操作条
│ 房间名(可留空)   │
│ ┌──────────────┐ │
│ │    建  房     │ │
│ └──────────────┘ │
└──────────────────┘
```

- 原来的 `HBox/Left`(在线+聊天)和 `HBox/Right`(房间+建房)合并成一列。
- 分段切换用**三个 `toggle_mode` `Button` + 一个 `ButtonGroup`**,配三个兄弟面板
  `Rooms` / `Online` / `Chat`(节点名用 ASCII,因为 `.gd` 里的路径是硬编码字符串),
  由 `_show_segment()` 按 key 切 `visible`。
  **为什么不用 `TabContainer`**(设计期原本写的就是它):页签是手机上的主导航,
  必须够大,而 `TabContainer` 的页签高度由主题 StyleBox 的内边距决定 ——
  想做到 48 得自己写一整套 StyleBox,等于重做外观。`Button` 一个
  `custom_minimum_size` 就够了。
- 「建房」操作条**始终可见**,不随分段切换 —— 它是主操作。
- 「刷新」按钮删掉:列表本来每 3 秒自动轮询,手机上这个按钮只是占地方。

## 6. 触控尺寸收进主题(**不做** —— 实施期推翻)

设计期的想法是把控件最小高度收进 `family.tres`。**实施时放弃了**,两个理由:

1. **不需要。** 实测各场景现有的 `custom_minimum_size` 已经全是 44~56 **逻辑**像素,
   一个不缺 —— 手机上点不到纯粹是被 0.30 缩放害的。基准分辨率一改就都到位。
2. **代价太大。** Godot 的 `Theme` **没有** min-height 这种属性,控件最小高度是
   字号 + StyleBox 内边距算出来的。想用主题控制就得给 Button/LineEdit/OptionButton/
   CheckButton 各写 normal/hover/pressed/disabled 四套 StyleBoxFlat —— 等于重写一套
   外观,风险远大于收益。

⚠️ **但设计期漏算了一件事:** 因为 432 已经**等于或大于**最宽的真机(430 CSS px),
所有手机的缩放系数都 ≤ 1.0(390 宽 → 0.903,360 宽 → 0.833)。所以按 **44** 逻辑单位
画的控件在真机上只有:

| 机型 | 缩放 | 44 单位 | 48 单位 | 52 单位 |
|---|---|---|---|---|
| 430×932 | 0.995 | 43.8pt | 47.8pt | 51.8pt |
| 390×844 | 0.903 | **39.7pt** | 43.3pt | 46.9pt |
| 360×800 | 0.833 | **36.7pt** | 40.0pt | 43.3pt |

44 在主流机上差 10%、小屏上差 17%。所以实施时把**所有 44 提到 48**(大厅的三个
页签、房间的「离开」)。48 在主流机上是 43.3pt,基本贴住 44pt 这条线;要在 360 宽
上也严格 ≥44pt 得用 52,但那会让次要控件和主 CTA 一样大,不值得 —— 48 远高于
WCAG 2.5.8 AA 的 24px 底线。

## 7. 验证

| 层 | 怎么做 | 结果 |
|---|---|---|
| 节点路径 | `check_scenes.gd` —— 场景重构会让它报错,这是**预期**的,顺手更新 `.gd` 里的硬编码路径 | 30 路径 / 4 场景,0 失败 |
| 竖屏可玩 | `tools/web_smoke.py` 加手机档位(390×844 设备模拟),断言逻辑视口宽度 ≤ 480 + 登录→大厅走通 | ✅ |
| 桌面没退化 | 同一个脚本的桌面档位 | ✅ |
| 分段切换 | 无头 Chrome 逐个点三个页签截图(冒烟测试不点页签,这部分只能单独验) | ✅ 三个面板正确切换,建房区始终可见 |
| 竖屏打整局 | 陪练机器人当第二个玩家,浏览器侧:建房 → 准备 → 开局 → 打完 → 离开 → 回大厅 | ✅ |
| 肉眼 | `docs/screenshots/*.png` 四张重新生成(432×700 竖屏画幅) | ✅ 中文与 `✊ ✋ ✌` 都正常 |

⚠️ **`web_smoke.py` 覆盖到哪儿为止,必须说清楚**,否则「两个档位全绿」会被误当成
「手机上全都验过了」:

- 它只走到**大厅**。房间页、猜拳页的布局它一行都不碰(`Page.click` 有,但登录流程
  已经不用坐标了,没有调用方)。
- 唯一的几何断言是**逻辑视口宽度**,而且是在**登录页**打印的。大厅布局整个塌了
  它照样绿。
- **只查宽度,不查高度。** 被挤到 844px 视口外面的控件它看不见(Godot 的 Control
  不会自动滚动)。
- 每个档位只登**一个**客户端,多人同时出拳这类交互它测不到。
- 手机档位**不开触摸模拟**(理由见 §8),所以驱动它的是鼠标键盘事件,不是真触摸。

## 8. 已知限制

- **真机上的文字输入这套测试完全没覆盖到。** 这是实施期最重要的发现:
  `export_presets.cfg` 开了 `html/experimental_virtual_keyboard`,而 Godot Web 的
  `FEATURE_VIRTUAL_KEYBOARD` 是按**运行时触屏探测**(`'ontouchstart' in window`)
  开关的。`LineEdit.virtual_keyboard_enabled` 默认 true,于是在触屏设备上
  `grab_focus()` 会让 Godot 新建并聚焦一个贴在 canvas 旁边的**隐藏 DOM `<input>`**
  来接软键盘输入 —— 打在 canvas 上的键事件根本进不去。
  这也是为什么冒烟测试的手机档位**不能**开 `Emulation.setTouchEmulationEnabled`:
  一开它登录就永远走不完(五组对照实测确认,且单独开它、不带 metrics override
  照样卡)。代价就是这条真机输入路径只能人工验。
- **软键盘遮挡。** 聊天输入框获得焦点时软键盘可能挡住内容。顺带查清了一件事:
  上游 `godotengine/godot#76215`(开虚拟键盘后 Enter 不触发 `text_submitted`)
  已由 PR #113461 修复、合入 **4.6** 里程碑,早于本项目用的 4.7.2,所以大概率
  已经好了 —— 但那个 PR 自称 "partially fixes",**键盘遮挡这一半可能还在**。
  登录页因此不依赖回车:「进入大厅」按钮才是主路径,回车只是顺手多一条。
- **手机横屏更小了。** 基准高度从 640 提到 700 之后,844×390 的缩放从 0.609 掉到
  0.557,44 单位的按钮从 26.8pt 掉到 24.5pt。这是竖屏优先的既定代价(§2 决策 1),
  记在这里免得以后当成新 bug 查。
- **平板偏大。** 768×1024 缩放 1.46,内容列占屏宽 83%,按钮 64pt+。能用,但没利用
  平板的屏幕。想做好得给平板单独一档布局,超出本次范围。
- **`ItemList` 的触摸滚动手感**未在真机验证过,无头浏览器测不出手感。
- **标签页隐藏时引擎停转。** 不是本次引入的,但手机上切后台/锁屏必然触发,靠
  `ensure_socket_async()` 的断线自愈兜住(commit `6db2af1`)。
